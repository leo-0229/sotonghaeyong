# 임시 계정 발급 → 최초 로그인 변경

학생이 직접 신상 정보를 입력해 가입하는 방식 대신, 학교에서 확인한 **학번·이름·성별을 운영자가 등록**합니다. 발급한 임시 아이디·비밀번호로 로그인하면 본인 정보를 확인하고 새 아이디·비밀번호를 설정합니다. 변경 전에는 커뮤니티를 이용할 수 없습니다.

## 운영 서버 준비

1. Supabase에 SQL `001 → 002 → 003_temporary_accounts.sql → 004_pilot_release.sql`을 순서대로 적용합니다. 이미 적용한 마이그레이션을 다시 실행하지 않습니다.
2. 기존 공개 Supabase URL/키 설정을 사용합니다. 실제 이메일을 로그인 아이디로 요구하지 않습니다.
3. `ALLOWED_ORIGINS`를 설정하고 계정 처리 함수를 배포합니다.

```powershell
supabase functions deploy account-access
```

함수는 요청의 실제 Auth 토큰을 검증합니다. 계정 발급은 최초 정보 변경을 마친 LEVEL 5 교사만 할 수 있습니다. 서비스 키는 Edge Function에서만 사용합니다.

## 임시 운영 계정 수

현재 L1~L5 각 1명, 총 5명만 발급합니다. L2는 반장·부반장 중 한 명, L4는 회장단·홍보부장 중 한 명입니다. 같은 레벨의 두 번째 발급은 DB에서 거부하며 아직 비밀번호를 바꾸지 않았거나 정지·탈퇴한 계정도 포함합니다. [임시 배포 설계](PILOT_RELEASE.md)를 참고하세요. 로컬 가상 예시 회원은 실제 발급 계정이 아닙니다.

## 최초 교사 계정

Node.js 24에서 `.env.admin.local`의 운영자 설정을 사용해 최초 교사 임시 계정을 발급합니다.

```powershell
cd C:\Users\user\Desktop\mpms
npm.cmd run provision -- --name 담당교사 --role SUPERVISING_TEACHER
```

무작위 임시 아이디와 비밀번호를 터미널에 한 번 출력합니다. 해당 담당자에게 개별 전달하세요. 교사도 첫 로그인에서 새 아이디·비밀번호를 설정해야 교사 권한을 사용할 수 있습니다. 비밀번호를 명령행 인자로 넘기거나 저장소에 저장하지 않습니다.

## 학생 계정 발급

교사 로그인 후 **교사 관리 → 임시 계정 발급**에서 다음을 등록합니다.

- 학번: `20315` 또는 `2315` 모두 2학년 3반 15번으로 처리하고 `20315`로 정규화합니다. 현재 초안은 1~3학년·1~6반·01~99번을 지원합니다.
- 이름: 학교에서 확인한 실제 이름.
- 성별: 학교에서 확인한 값. 동성 1:1 멘토링에 사용합니다.
- 등급: 일반 학생을 기본으로 LEVEL 1~4 선택. 반장·부반장은 직책도 지정합니다.

임시 아이디와 비밀번호는 무작위로 생성됩니다. 발급 결과는 해당 화면에 한 번 표시하며 새로고침하거나 화면을 떠나면 다시 표시하지 않습니다. **개별 전달용 복사**로 복사한 뒤 해당 학생에게만 전달하세요. 공개 게시판에 올리지 않습니다. 같은 학급·학번의 중복 발급은 서버에서 거부합니다.

필요하면 운영자 CLI로도 발급할 수 있습니다.

```powershell
npm.cmd run provision -- --student-id 20315 --name 가상학생 --gender FEMALE
npm.cmd run provision -- --student-id 30105 --name 가상임원 --gender MALE --role COUNCIL_OFFICER
npm.cmd run provision -- --student-id 20301 --name 가상반장 --gender FEMALE --role CLASS_OFFICER --position CLASS_PRESIDENT
```

## 학생의 첫 로그인

1. 전달받은 임시 아이디·비밀번호로 로그인합니다.
2. 학번·이름·학급·성별을 확인합니다. 다른 사람의 정보라면 변경을 진행하지 말고 담당 교사에게 알립니다.
3. 현재 임시 비밀번호를 확인하고 새 아이디·새 비밀번호를 입력합니다.
4. 새 비밀번호 확인과 본인 정보 확인을 마친 뒤 **로그인 정보 변경 완료**를 누릅니다.
5. 새 정보로 세션을 발급받아 커뮤니티로 이동합니다. 기존 임시 아이디·비밀번호는 더 이상 로그인에 사용할 수 없습니다.

변경 요청 도중 네트워크가 끊겨 결과를 확인하지 못한 경우에는 새 아이디·비밀번호로 다시 로그인해 변경 여부를 확인하세요.

아이디는 영문 소문자로 시작하는 4~24자 영문·숫자·밑줄을 지원하며 `tmp_`는 임시 계정 전용입니다. 기존과 다른 아이디와 기존과 다른 12~128자 비밀번호를 사용합니다. 이미 사용 중인 아이디는 등록할 수 없습니다.

이 화면에서 학번·이름·성별은 수정하지 못합니다. 이 정보는 Auth의 사용자 입력 메타데이터가 아니라 학교가 등록한 프로필에서 가져옵니다. 학번·로그인 아이디는 본인과 담당 교사에게만 제공하며 공개 게시판에 표시하지 않습니다.

## 저장과 접근 보호

- 내부적으로는 로그인 아이디를 `accounts.mpms.invalid` 예약 도메인의 Auth 주소에 대응시킵니다. 실제 개인 이메일이나 이메일 인증을 요구하지 않으며 메일을 발송하는 용도가 아닙니다.
- 비밀번호는 Supabase Auth가 관리합니다. 프로필·감사 로그·브라우저 저장 데이터에 평문 비밀번호나 별도 비밀번호 해시를 복사하지 않습니다.
- 최초 변경 전에는 서버 `current_level()`도 0을 반환해 콘텐츠 조회·제출·관리 작업을 거부합니다.
- Auth에서 실제 아이디 주소와 비밀번호 해시가 모두 변경된 것을 DB 트리거로 확인한 뒤 잠금을 해제합니다. 클라이언트가 변경 완료 플래그를 보내 잠금을 풀 수 없습니다.
- 변경 전 기존 모든 세션의 refresh token을 취소합니다. 새 로그인 정보가 저장되면 자격 증명 버전이 바뀌므로 변경 전 JWT도 커뮤니티 권한을 잃습니다. 새 로그인 정보로 다시 발급한 세션만 이용합니다.
- 계정 발급·변경 요청에 빈도 제한을 적용하고 로그에는 계정 발급·변경 사실만 남깁니다.

## 로컬 체험과 검증 한계

Supabase 설정이 없는 localhost 개발 모드에서도 교사 체험 계정으로 발급 화면과 최초 변경 흐름을 확인할 수 있습니다. **로컬 체험은 실제 비밀번호 인증을 하지 않으며 비밀번호를 저장하지 않습니다.** 실제 개인정보나 실제 사용하는 비밀번호를 입력하지 마세요.

Supabase 프로젝트가 아직 없으므로 실제 Auth 계정 발급·비밀번호 변경 원격 호출은 실행하지 않았습니다. 로컬 PostgreSQL에서 권한·트리거·이전 JWT 버전 차단을 검사하고 브라우저에서 전체 화면 흐름을 검사합니다. 운영 연결 후 실제 Auth API에서도 재검증해야 합니다.
